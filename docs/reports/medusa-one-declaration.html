One Declaration, Both Planes

Frappe kept enrichment and linking in two unrelated mechanisms that happen to share a tab strip. Medusa emits both from a single defineLink call — and then adds a third form for edges that already exist, which is the idea worth stealing.

reference/medusa, shallow clone, 2026‑09‑15 Reference case: ProductVariant ↔ InventoryItem Read against this repo's registry and benchmark

The finding in one paragraph

defineLink compiles into a config with two sections: relationships, which creates a pivot table owned by a third module, and extends, which grafts a queryable field onto both endpoints' entities. ProductVariant.inventory becomes resolvable on an entity owned by a module that has never heard of inventory — with no column added to product_variant and no code changed in the product module.

That is ERPNext's Manufacturing tab without putting default_bom on tabItem. Same user-visible affordance, opposite storage decision.

One — the fused declaration

Edge and enrichment, emitted together.

// src/links/product-inventory.ts — in an app or a plugin
export default defineLink(
  ProductModule.linkable.productVariant,
  InventoryModule.linkable.inventoryItem,
  { database: { table: "product_variant_inventory_item",
                extraColumns: { required_quantity: { type: "decimal" } } } }
)

compiles to (define-link.ts:200):

relationships: [                       // the EDGE — a real pivot table
  { serviceName: Modules.PRODUCT,   entity: "ProductVariant",
    primaryKey: "id", foreignKey: "variant_id",        alias: "variant" },
  { serviceName: Modules.INVENTORY, entity: "InventoryItem",
    primaryKey: "id", foreignKey: "inventory_item_id", alias: "inventory" },
],
extends: [                             // the ENRICHMENT — query-graph grafts
  { serviceName: Modules.PRODUCT, entity: "ProductVariant",
    fieldAlias: { inventory: "inventory_items.inventory" },
    relationship: { serviceName: LINKS.ProductVariantInventoryItem,
                    primaryKey: "variant_id", foreignKey: "id",
                    alias: "inventory_items", isList: true } },
  { serviceName: Modules.INVENTORY, entity: "InventoryItem",
    fieldAlias: { variants: { path: "variant_link.variant", isList: true } },
    relationship: { ... } },
],

generate-entity.ts then builds a MikroORM EntitySchema at runtime from that config: two foreign keys as a composite primary key, extraFields as real columns, soft-delete timestamps, table name run through compressName for Postgres' 63-character identifier limit.

A link is a module in its own right — own service name, own table, own migrations, own id prefix. Neither endpoint owns it. That is LinkTypeDecl plus a storage layer, packaged as one call.

Two — three kinds of link

The read-only link is the one we are missing.

The default writable link creates a pivot table because the edge did not exist. But some edges already do — and Medusa declares that case explicitly, storing nothing:

export const CartCustomer: ModuleJoinerConfig = {
  isLink: true,
  isReadOnlyLink: true,          // no relationships, no databaseConfig, no table
  extends: [
    { serviceName: Modules.CART, entity: "Cart",
      relationship: { serviceName: Modules.CUSTOMER, entity: "Customer",
                      primaryKey: "id", foreignKey: "customer_id",
                      alias: "customer" } },
    { serviceName: Modules.CUSTOMER, entity: "Customer",
      relationship: { serviceName: Modules.CART, entity: "Cart",
                      primaryKey: "customer_id", foreignKey: "id",
                      alias: "carts", isList: true } },
  ],
}

link-modules/src/definitions/readonly/cart-customer.ts

cart.customer_id is already a column on the cart. The declaration only tells the query planner that the column is a reference into another module's entity, so cart.customer.email resolves. Fifteen ship in the box: cart-product, order-region, store-currency, line-item-adjustment-promotion, product-translation.

This is the distinction Frappe draws between get_internal_links and get_external_links — but inferred there at count time, and declared here up front. defineLink enforces the asymmetry at boot:

if (!leftService.linkable || !leftService.field) {
  throw new Error(`ReadOnly link requires "linkable" and "field" ...`)
} else if (leftService.filterable || rightService.filterable) {
  throw new Error(`ReadOnly link does not support filterable fields.`)
}

And a third: the Index module

packages/modules/index takes the exact fork architecture.md identifies — refs or denormalized summaries — and answers both, in two tables:

const IndexData = model.define("IndexData", {
  id: model.text().primaryKey(),
  name: model.text().primaryKey(),      // entity type
  data: model.json().default({}),       // the denormalized summary
  staled_at: model.dateTime().nullable(),
})

const IndexRelation = model.define("IndexRelation", {
  id: model.autoincrement().primaryKey(),
  pivot: model.text(),
  parent_name: model.text(), parent_id: model.text(),
  child_name: model.text(),  child_id: model.text(),
  staled_at: model.dateTime().nullable(),
})

IndexRelation is our link_index almost column for column. IndexData is the summary half we declined to build. The part worth stealing is how it is configured — not by code, and not by satellites pushing after commit, but by a GraphQL schema carrying a @Listeners directive:

type Product @Listeners(values: [
  "product.product.created", "product.product.updated",
  "product.product.deleted", "product.product.restored"
]) {
  id: ID
  title: String
  handle: String
  variants: [ProductVariant]
  sales_channels: [SalesChannel]
}

index/src/utils/default-schema.ts

registerListeners() walks that schema, subscribes each declared event to consumeEvent, and does so only in worker mode (if (!this.#isWorkerMode) return). The shape of the index, the events that invalidate each part of it, and the projection stored are one declaration. Rows are marked staled_at rather than deleted.

Three — the linkable contract

A module publishes what may be linked, and boot enforces it.

Module.linkable is generated, not written. buildLinkConfigFromModelObjects walks each model's schema and emits an entry for every primary key or id property:

{ linkable: "product_variant_id",   // the foreign key a link will use
  primaryKey: "id",
  serviceName: "product",
  field: "productVariant",
  entity: "ProductVariant" }

and defineLink validates against it before the app boots:

const serviceAKeyEntity = serviceAInfo.linkableKeys?.[serviceAObj.key]
if (!serviceAKeyEntity) {
  throw new Error(`Key ${serviceAObj.key} is not linkable on service ${serviceAObj.module}`)
}
if (!moduleAPrimaryKeys.includes(serviceAPrimaryKey)) {
  throw new Error(`Primary key ${serviceAPrimaryKey} is not defined on service ${serviceAObj.module}`)
}

A module also opts in to being queryable at all — definition: { isQueryable: true } — and the error message quotes the config block you need to write.

Contract we do not have

RegisterLinkType accepts any source_type/anchor_type pair with no check that the anchor's owner considers that key stable and referenceable. Registration-time failure beats a dangling reference discovered on the item screen.

Four — reading and deleting

A real query planner, and a cascade that only apologises.

The graph planner is a documented three-stage pipeline: GraphCatalog (index configs) → compileQuery (query → plan) → executePlan (fetch, join, shortcuts). Loading sits behind IRemoteDataFetcher, so the planner is indifferent to whether a module is in-process or remote.

The part most federated designs skip is there too: cross-module-joins/rewrite-filters.ts (410 lines) and residual-filters.ts (400 lines) decide which filters push down to which module and which must run after the join — because a filter on product.variants.inventory.location_id spans three services and only some of it can travel. Our GetLinks has no equivalent, and will need one the first time a caller filters across a link rather than listing.

Deletes are best-effort

if (joinerConfig.isLink && !relationship.deleteCascade) {
  continue                                  // opt-in only
}
...
} catch (error) {
  errors.push({ serviceName, method, args: cascadeDelKeys, error: ... })
  return                                    // keep walking
}
...
return [errors.length ? errors : null, result]

core/modules-sdk/src/link.ts — executeCascade

A breadth-first walk over the relations map, calling softDelete on each related service, collecting failures into an array rather than aborting. No distributed transaction, no retry, no durable record of what failed. A caller that ignores the error tuple silently orphans rows.

Where we are already stronger

The transactional outbox in services/pim plus doclink.deliveries with attempts and last_error gives bounded retry and a durable record of giving up. Medusa's cascade works because every module is usually in one process against one database.

Five — the write path

additional_data is the answer we don't have.

The question Frappe answers with ALTER TABLE — how does satellite data get in when the user submits the anchor's form? — Medusa answers without touching the anchor's schema at all:

const productsCreated = createHook("productsCreated", {
  products: response,
  additional_data: input.additional_data,
})

return new WorkflowResponse(response, { hooks: [productsCreated] })

core-flows/src/product/workflows/create-products.ts:281

additional_data is an opaque bag the core workflow never reads — it validates it against a plugin-supplied validator and forwards it. A plugin registers a handler on createProductsWorkflow.hooks.productsCreated, receives the created products and the bag, and writes its own row plus the link. The product API schema does not grow, and neither does the product table.

That is the missing half of our design. We have a read plane and a lifecycle plane, and nothing that lets a satellite receive data a user typed on the anchor's form.

Six — the UI plane

Here Medusa is the worked example of what we refused.

Admin extension points are injection zones with a familiar taxonomy — product.details, product.details.side, product.list, order.details. The file even records the migration away from .before/.after suffixes because "the layout composer handles ordering with drag&drop", which is our weight field learned the hard way.

But the zone list is a compile-time TypeScript union, extended by declaration merging:

export type InjectionZone = keyof InjectionZoneRegistry

// a plugin, in index.d.ts:
declare module "@medusajs/admin-shared" {
  interface InjectionZoneRegistry {
    "my-plugin.product-page": true
    "my-plugin.product-page.side": true
  }
}

and discovery is a build step. admin-vite-plugin Babel-parses every widget file, reads the defineWidgetConfig object literal, and emits a virtual module:

export default { widgets: [
  { Component: WidgetComponent_0, zone: ["product.details"], widgetId: "..." },
] }

Every widget is statically imported into the admin bundle, runs in the host's JS realm, and the extension set is frozen at build time. A new plugin means rebuilding and redeploying the admin. Medusa buys a shared theme, a shared router, no postMessage and no height negotiation — and pays with decoupling by etiquette and a deploy coupling between host and satellite. That trade is precisely the one architecture.md declines.

Seven — registration, isolation, tenancy

A global, a shared schema, and no tenants.

Registration is an import side effect — global.MedusaModule.setCustomLink(register) at module scope. The loader's own comment says the rest:

Load links from the source paths, links are registering themselves, therefore we only need to import them

Source paths are join(plugin.resolve, "links") for every resolved plugin, so discovery is filesystem convention over node_modules at boot. No registry table, nothing queryable at runtime, nothing a tenant can toggle.

Isolation is opt-in and unenforced. Each module reads PRODUCT_DATABASE_URL → MEDUSA_DATABASE_URL → DATABASE_URL, and schema defaults to "public". By default every module shares one connection, one database and one schema; nothing stops a raw query joining product to inventory_item. Compare 0007_roles.sql here, where a cross-schema join fails with permission denied for schema pim. That is the difference between a boundary and a guideline.

On the marketplace question specifically

Modules are listed in medusa-config.ts; plugins resolve from node_modules at boot. One deployment serves one merchant. There is no per-tenant activation, no install state, no equivalent of Frappe's disabled_apps. Frappe is the better reference here and Medusa has nothing to say.

Nine — what to take

Five borrowings, and four things to leave.

01

Declare the "edge already exists" case

Second independent confirmation — Frappe infers it at count time, Medusa declares it and stores nothing. We force a linkage table even when the reference is already a field the satellite holds for its own reasons.

enum LinkStorage {
  LINK_STORAGE_UNSPECIFIED    = 0;
  LINK_STORAGE_OWNED_TABLE    = 1;  // today's only mode
  LINK_STORAGE_EXISTING_FIELD = 2;  // anchor ref is already a column
}

GetLinks skips a traversal hop for mode 2 and goes straight to resolution; ResolveLinks implementations stop writing a redundant row.

02

Let the edge carry properties

extraColumns: { required_quantity: { type: "decimal", defaultValue: "1" } }. "This variant needs two of that inventory item" is a fact about the edge, not either endpoint, and we have nowhere to put it — a satellite either smuggles it into its own row or invents a side table. Add a small typed edge_fields declaration to LinkTypeDecl.

03

Validate the linkable surface at registration

Extend DocumentType to publish the keys its owner considers stable and referenceable, and reject a LinkTypeDecl naming a key that was never published — the way defineLink fails at boot rather than on the item screen.

04

Give the index a declarative invalidation contract

Our link_index is written by satellites after their own commit, with nothing anywhere stating what makes a row stale. Put the subscribing events on LinkTypeDecl beside subscribes_to_lifecycle, add staled_at to doclink.link_index, and let the registry stale rows on lifecycle delivery instead of waiting for a correction push.

Keep storing refs only. The benchmark already says summaries buy flatness at the cost of a far wider staleness surface — IndexData is that trade taken.

05

Build the write plane

An opaque additional_data map on PIM's create and update mutations that PIM never reads, validated against a schema each contributing module registers, and forwarded verbatim on the lifecycle event. The satellite reacts to item.created with the bag and writes its own row. PIM's API schema does not grow, and no satellite sits inside PIM's write transaction.

What not to take

  • Build-time extension discovery. Babel-scanning widgets into the host bundle freezes the extension set at build and puts every satellite in the host's JS realm.
  • A global mutable registry. global.MedusaModule.setCustomLink at import time is fine for one process and meaningless across services.
  • Shared-schema-by-default. schema: "public" for every module makes the boundary a code-review rule. Keep the role grants.
  • Best-effort cascade. Returning an error array is weaker than a durable outbox. Keep ours.

Frappe separated the two planes and coupled the teams. Medusa fused the two planes and decoupled the teams — then spent the decoupling again on a build-time UI registry and a shared default schema. The parts worth taking are the small declarative ones: an edge that can already exist, an edge that can carry properties, a linkable surface that boot can check, and an index that says out loud what makes it stale.
