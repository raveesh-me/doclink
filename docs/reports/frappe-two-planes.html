Two Planes of the Item Screen

ERPNext shows Sales, Tax, Quality, Manufacturing as tabs on an Item, and Quotation, Sales Order, BOM, Batch as connections below it. They look like peers. They share no code, no storage model, and no extension mechanism.

Plane one — schema composition

The tabs are not modules. They are one file.

There is no "Sales module contributing to Item" in ERPNext. Sales, Tax, Quality and Manufacturing are Tab Break fields inside a single 135-field doctype definition owned by one module, and the fields beneath them are plain columns and child tables on the same row.

The giveaway is module ownership. A Frappe child table is physically a parent/parenttype row set and must be declared as a Table field on its parent — so it cannot live in the module that owns its meaning:

Item                  module=Stock  istable=0
Item Tax              module=Stock  istable=1   <- tax semantics
Item Default          module=Stock  istable=1   <- accounting semantics
Item Customer Detail  module=Stock  istable=1   <- selling semantics

Three teams' schemas, one team's file

This is the "columns on the anchor" failure mode from docs/architecture.md, shipped at scale and mostly working. It works because ERPNext is one repository, one release train, one maintainer group. It is not a decoupling mechanism and never claimed to be.

The escape hatch, and its price

An app that is not erpnext enriches Item through Custom Field and Property Setter, shipped as fixtures and synced on install. That path is real DDL:

def on_update(self):                      # custom_field.py:218
    ...
    frappe.clear_cache(doctype=self.dt)
    frappe.db.updatedb(self.dt)           # ALTER TABLE tabItem ADD COLUMN

The assembly order in Meta.process() is what makes the result coherent — custom fields merged, property setters applied over them, field order resolved via insert_after, then custom links and actions:

def process(self):                        # frappe/model/meta.py:165
    self.add_custom_fields()              # :408  merge tabCustom Field rows
    self.apply_property_setters()         # :428  override label/hidden/reqd/options
    self.init_field_caches()
    self.sort_fields()
    self.get_valid_columns()
    self.set_custom_permissions()
    self.add_custom_links_and_actions()   # :477  ← the other plane leaks in here
    self.check_if_large_table()

Uninstall is a display filter, not a migration: is_field_hidden_by_app() hides a field owned by a disabled app, and also any Link or Table field pointing at a doctype that app owns. The column stays in the table.

So the field plane has two tiers, compile-time and install-time, and no runtime tier. Nothing here discovers a field at page load.

Plane two — curated reverse links

The connections panel stores no edges.

The entire second screenshot is one dictionary in one file:

Read what this is and is not. The edge is tabSales Order Item.item_code — a column on the satellite. The anchor holds nothing, which is the same inversion this repo argues for. fieldname is a convention ("assume everyone refers to me through item_code"); non_standard_fieldnames patches the exceptions. And transactions is grouping and ordering only — it is not the set of things that link to Item. That set is computed elsewhere, automatically, and is much larger.

Three ways in, chained in app order

def get_dashboard_data(self):                    # frappe/model/meta.py:768
    data = frappe._dict()
    if not self.custom:
        module = load_doctype_module(self.name, suffix="_dashboard")
        if hasattr(module, "get_data"):
            data = frappe._dict(module.get_data())    # 1. file convention

    self.add_doctype_links(data)                      # 2. DocType Link rows, custom=1

    if not self.custom:
        for hook in frappe.get_hooks("override_doctype_dashboards", {}).get(self.name, []):
            data = frappe._dict(frappe.get_attr(hook)(data=data))   # 3. hook chain
    return data
  1. File convention. <doctype>_dashboard.py in the owning app. Only the owner writes this.
  2. DocType Link child rows. link_doctype, link_fieldname, group, parent_doctype, table_fieldname, is_child_table, hidden, custom. Rows flagged custom=1 are pulled from the database at meta-build time, so any installed app — or a site admin through Customize Form — adds a connection group without editing the anchor's source. This is the closest thing Frappe has to a Contribution.
  3. override_doctype_dashboards. One function per app, chained, each handed the accumulated data. Full mutation rights, including deletion.

Resolution, and where it gets defensive

@frappe.whitelist()

Each doctype in the groups resolves as one of two shapes:

  • External (:359) — the satellite carries the column. count(*) WHERE item_code = ?, plus a second count under the doctype's "open" filters for the orange badge. When the fieldname sits on several child tables of one parent, :380 switches to an or_filters name list capped at 100, because a filter on an ambiguous fieldname silently resolves to whichever child table joins first.
  • Internal (:313) — the anchor holds the value, directly or inside one of its own child tables. No query at all: read the already-loaded document and count distinct values.
  • And because pairs get created in either direction — a Sales Invoice made from a Delivery Note versus one a Delivery Note was made from — :290 probes the external direction when the internal one comes back empty.

On the client, filter_permissions() drops unreadable doctypes cosmetically (the server already enforced via get_lazy_doc(..., check_permission=True)), render_links() paints the template once, and the + button calls frm.make_new(doctype, fieldname), which prefers an app-supplied make_methods entry and otherwise scans the target's meta for a Link field whose options is the current doctype, then pre-fills it.

All of it mounts into a section literally labelled Connections, which ERPNext parks under a dashboard_tab Tab Break. That is the only thing the two planes share: a tab strip.

Plane two, continued — the truth underneath

The real link graph is a SELECT.

filters = [["fieldtype", "=", "Link"], ["options", "=", doctype]]
links  = frappe.get_all("DocField",     fields=["parent", "fieldname"],       filters=filters)
links += frappe.get_all("Custom Field", fields=["dt as parent", "fieldname"], filters=filters)

frappe/desk/form/linked_with.py:978 — get_linked_fields

This is the load-bearing fact about the whole framework. The schema is stored as documents — tabDocType, tabDocField, tabCustom Field, tabDocType Link are ordinary tables in the same database as the data. So "who links to Item?" is a query, not a registry anyone maintains, and the answer includes edges a third-party app added five minutes ago.

That derived graph drives deletion and cancellation cascades, the Links button, and link integrity on delete. A module opts out with exclude_from_linked_with = True.

The relationship between the dashboard and the derived graph: the derived graph is the truth, the dashboard is the curation. The panel exists because the full graph is too large and unordered to put on a screen — not because it is missing anything.

And a fourth mechanism: polymorphic satellites

Dynamic Link (istable=1)
  link_doctype  Link          -> DocType
  link_name     Dynamic Link  -> link_doctype
  link_title    Read Only

Contact and Address hold a child table of these. One Address attaches to a Customer, a Supplier and a Lead at once, with zero columns on any of them and zero foreign keys anywhere — the row-level version of the same inversion.

The price is in frappe/model/dynamic_links.py. To know which doctypes a dynamic link actually points at, it runs SELECT DISTINCT over the whole satellite table and caches for twelve hours, admitting in its own docstring that results "can possibly be outdated" and a cache miss "can often be VERY expensive on large table". Raw SQL writes never invalidate it.

Polymorphism without a declaration means the type set must be discovered by scanning data. That is precisely what link_types in this repo exists to avoid.

Why it holds — three properties we do not have

Frappe affords all four mechanisms by being single-tenant.

  1. Metadata is data, in the same database. Reverse-link discovery is a join. A registry lookup is a local query, not a network hop.
  2. One database per tenant. A Frappe "site" is a database. Custom Field, DocType Link and Property Setter rows are per-site. Per-tenant schema divergence is achieved with per-tenant ALTER TABLE — sane only at hundreds of tenants, not hundreds of thousands.
  3. Apps are code on the bench, activated per site. _load_app_hooks() iterates get_active_apps() and imports <app>.hooks; app_state.py derives disabled modules and doctypes from disabled_apps, and every meta build, list query and permission query filters against them.

The marketplace answer, stated precisely

Frappe's marketplace is per-tenant activation of code that is already deployed. Installing an app writes rows and runs DDL on one tenant's database. It never loads code at runtime, and a tenant cannot have an app the bench does not have.

That is the same shape as "some modules hardcoded at code time" — Frappe simply makes every module that shape and varies only the activation.

Recommendations — six changes

Model the activation dimension, not the field plane.

1 · Tenancy is a security boundary, and it is absent

Nothing in proto/doclink/v1/* or internal/pg/migrations/0005_doclink.sql carries a tenant, and contributions is UNIQUE (extension_point_id, namespace) globally. Model it as two tables so declaration count stays proportional to modules, not tenants × modules:

-- code-time identity: one row per module that exists in the world
CREATE TABLE doclink.modules (
    module_key  TEXT PRIMARY KEY,      -- "subscriptions"
    source      TEXT NOT NULL,         -- 'builtin' | 'marketplace'
    publisher   TEXT NOT NULL
);

-- per-tenant activation: the Frappe "installed app" row
CREATE TABLE doclink.module_installations (
    tenant_id   TEXT NOT NULL,
    module_key  TEXT NOT NULL REFERENCES doclink.modules,
    state       TEXT NOT NULL,         -- 'active' | 'suspended' | 'uninstalling'
    PRIMARY KEY (tenant_id, module_key)
);

contributions and link_types stay tenant-free — they describe code, registered at module boot, exactly as today. The tenant filter is a join on the read path:

SELECT c.* FROM doclink.contributions c
JOIN doclink.module_installations i
  ON i.module_key = c.namespace AND i.tenant_id = $1 AND i.state = 'active'
WHERE c.extension_point_id = $2
ORDER BY c.weight DESC, c.title;

Non-negotiable

tenant_id comes from the request's auth context inside the registry, never from a field the caller sets. A client-supplied tenant on ListContributions is a cross-tenant enumeration of who installed what. Same rule for GetLinks: the fan-out plan derives from the trusted tenant, and a module not installed for that tenant is not called — not called and filtered.

2 · builtin vs marketplace is metadata, never dispatch

A module compiled into the binary registers through the same RegisterContribution / RegisterLinkType calls at boot that a third-party module makes over the network. The source column exists so you can refuse to uninstall a builtin and so support can answer "where did this card come from" — not so any code path branches on it. The moment the shell contains if (contribution.source === 'builtin'), the property make verify asserts is gone.

The precedent is exact: erpnext is an app on the bench with the same lifecycle as any marketplace app, and core reads its hooks through the same loop.

3 · CSP and lifecycle derive from the installed set

services/webhost computes frame-src as registry contributions ∩ ALLOWED_EMBED_ORIGINS. With tenancy, the first term becomes this tenant's active installations, and a suspended module drops out of the header on the next page load. Same for the lifecycle fan-out: link_types … WHERE subscribes_to_lifecycle becomes that joined to active installations, or a satellite keeps receiving deletes for a tenant that offboarded it.

4 · Do not build the field plane. Build a slot for it.

The Sales/Tax/Quality tabs are the pattern this repo exists to refuse. A satellite that needs to appear as a tab gets a second extension point — pim/item:detail.tab — with the identical contract: anchor DocRef in, iframe out, satellite owns storage. Different slot, same plane, no anchor schema change.

The only fields belonging on pim.items are ones the PIM team would defend in review as intrinsic. If tenants genuinely need tenant-specific anchor-owned attributes, that is a third thing: a tenant-scoped, declared, validated attribute schema owned by PIM (pim.item_attribute_defs plus a typed value table), versioned and migrated by PIM. Not an open JSON bag, and not per-tenant DDL — Custom Field gets away with DDL only because of one database per tenant.

5 · Give LinkResolver a count-only call with a deadline

Frappe's badge counts are its operational weak point: an unbounded count(*) per connection, defended by a one-second statement timeout and a fail-open empty result. Reasonable under one database; worse over a network fan-out, where the card menu's question — "is there anything here?" — currently costs a full ResolveLinks.

Add CountLinks(anchor_ref) -> {count, open_count}, hold the per-satellite budget well under the existing 5s client timeout, and render an unknown badge on timeout rather than blocking the menu. The benchmark already argues for it: with refs_only, INDEXED goes flat at 4.3 ms across eighteen satellites. A count is the degenerate case of refs-only and should be served from link_index keyed (tenant_id, anchor_ref), federated path as the correctness fallback.

6 · Borrow the internal/external distinction

Some links the anchor genuinely holds — Item.default_bom is a column on the item, and Frappe counts it without a query because the value is already loaded. In our terms: when the anchor's own payload already contains a DocRef into another namespace, the answer needs a resolve for the display summary but not a traversal to find the edge. Worth a flag on LinkTypeDecl so GetLinks can skip a hop it does not need.

Frappe has one abstraction for enriching a document and a separate one for relating documents. This repo already picked the second and refused the first. The work left is not to add the first — it is to add the activation dimension Frappe gets for free by giving every tenant its own database, and to make every registry read path derive its fan-out from that, from trusted context, on the server.
